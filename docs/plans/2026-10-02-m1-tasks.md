## 2. 结构决策与 why

- **`Governor` 协议先落 context 包、不进 core**：M3 引擎消费时按 04 §5 演进规则升格——现在没有第二个消费者，先进 core 就是过度设计。
- **`keep_substrings` 钉住机制**：把"must-survive 全保留"从祈祷变成机器可判承诺；受保护内容本身就超预算时抛 `ContextBudgetError`，不静默丢弃。
- **启发式计数器**：tiktoken 的 BPE 词表要联网下载，违背 only-\* 离线承诺；M1 只要"确定性 + 量级正确"，精确计量经 `TokenCounter` 协议注入。
- **摘要走 Provider 端口**：压缩是内核"端口可消费性"假设的第一次真实检验——这是 M1 的第二使命；最坏情况会多轮生成摘要，正确性优先于调用数，调参随评测集。
- **卸载阈值固定常量**：M1 不做配置化（YAGNI）；它是策略参数，随评测集调参时再配置化。
- **契约套件经入口点组发现**：core 若内置 context 套件就是反向依赖；每包自注册（`tutelary.contract_suites`）是中立性的结构保证。工厂契约：`--tutelary-factory` 直接指向被测**组件类**，套件用 core 装配器 + fakes 装配驱动——检查的不只是行为，还有"能作为组件被装配"本身。
- **评测集不进 wheel**：`packages/context/evals/` 在包目录内、`src/` 之外，属开发材料。

## 3. 评测集 schema（09 M1 可判定判据）

`packages/context/evals/cases/` 下每案一个 JSON：

```json
{
  "id": "case-001",
  "transcript": [
    {"role": "user", "text": "……真实对话原文……"},
    {"role": "assistant", "text": "……"}
  ],
  "budget": {"total": 8000},
  "must_survive": ["必须原样保留的关键事实 / 决定", "……"]
}
```

两条硬指标：① 压缩后 history 实测 ≤ 预算 history 段；② `must_survive` 每条都出现在压缩输出中。

**状态：等待真实日志。**只有所有者能提供（自己的工作流即可，无需公开）；`cases/` 为空时运行器输出等待说明并正常退出——是待验收，不是失败。绝不拿想象日志调参（docs/09 认定的最大学习陷阱）。

## 5. 实现逼出的修订（同任务同步，工作草案规则）

- **工厂契约定型**：`--tutelary-factory` 直接指向组件类（原设想的"返回类的零参调用"是多余一层，04 §4 已同步）。
- **预算开箱默认值**：`Budget.total` 默认 8000——治理器不传配置也应可用；显式声明始终优先。
- **压缩先判后压**：预算内不动内容（原实现会无条件折叠一轮）；摘要实测后不达标继续折叠，最坏多轮 Provider 调用。
- **隔离矩阵的测试依赖**：包内测试需要 pytest-asyncio（asyncio auto 模式来自根配置），05 §5 已同步措辞。
