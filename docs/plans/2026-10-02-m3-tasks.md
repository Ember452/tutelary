## 2. 结构决策与 why

- **引擎直接消费 Provider/Tool/Policy/Memory 四端口；Sandbox 由沙箱化工具消费**（runtime 的 ExecTool requires Sandbox）——端口链在整船里全通，引擎不为"名义上消费五端口"硬造职责。这是有意决策，不是遗漏。
- **治理不经引擎**：Governor 端口留在 context 包，`Agent` 门面在 run 前后调用 enforce 并把全部事件桥接到 Bus（记忆写路径因此接通）。引擎保持与 context 零横向依赖——否则 Governor 必须升格进 core，等真实消费者再动。
- **引擎消费的 Tool 实为"工具带"**：引擎侧协议要求 `specs() -> tuple[ToolSpec, ...]` + `execute(call)`（按名字路由）；单提供者端口语义装不下 N 个工具，工具带由组合根（runtime）组装——与 policy 组合子同一条 M3 议题线。
- **事件流走门面桥接 Bus**：引擎只 yield 事件，门面逐事件 emit 到 Bus——观察者（记忆写路径）看到全部事件，引擎保持无 Bus 依赖。
- **Suspend 断点续跑的 M3 形态**：会话状态驻内存（messages + pending calls），resume( decisions) 从断点继续；持久化到磁盘是事件溯源的后续工程，不在 M3。
- **providers 的重试语义**：只在"尚未产出事件"的失败上重试/转移——流中途失败重试会重复输出，宁可上抛。
- **MockTransport 全离线**：两个协议适配与韧性包装的测试全部用 httpx MockTransport 脚本化 SSE，不联网（AGENTS §4.7）。
- **架构门禁同步**：门禁 2 给伞包豁免（组装者本就依赖全部组件，05 §3 措辞同步）；门禁 6 冒烟扩容 full-agent。
