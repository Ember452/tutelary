# 01 · 定位与竞争

状态：基线（2026-10-01）。本文回答"为什么做 Tutelary"。

## 1. 两个没人解决的痛点

**痛点一：治理缺位。** 主流开放框架都在解决"怎么编排"，没有一家把**运行时治理**（上下文预算、权限门、资源纪律、执行隔离）做成一等公民。上下文腐烂与成本失控是 Agent 生产事故的最大来源，各框架把它完全留给用户。

| 框架 | 核心抽象 | 治理现状 |
|---|---|---|
| LangGraph | 图编排 + checkpoint | 编排重，上下文治理 DIY |
| OpenAI Agents SDK | 轻循环 + handoff | 无上下文治理，安全靠自觉 |
| CrewAI | 角色化多 Agent | 工程治理几乎为零 |
| PydanticAI | 类型安全的工具/结构化输出 | 运行时治理缺位 |
| Claude Agent SDK | 产品级 harness（auto-compact 等） | 闭环但闭源生态绑定，不可自建复用 |

**痛点二：组件互锁。** 记忆产品（Mem0、Letta、Zep）与沙箱产品（E2B）各自要求"整体买进场"——采用一家意味着接受它的 API、它的存储、它的模型假设。互不兼容，没有互换契约，也没有中立的地方比较优劣。

## 2. 定位：可拆解的 Agent 基础设施

> **别把整个框架买回家——按需安装组件：上下文治理、记忆、沙箱、权限、循环，每一件都独立可装、独立可读、独立可发布。**

- 对"只需要一个组件"的用户：`pip install tutelary-context`，接进自己手写的循环；
- 对"要一个完整运行时"的用户：`pip install tutelary`，全家桶 + 开箱即用 Agent；
- 对"想换实现"的用户：契约测试保证任何符合 Port 的实现可互换（见 [06](06-extending.md)）。

这一定位同时是分发策略：组件比框架好传播（采用心理成本低一个量级），每个组件都能成为独立的 star 入口；伞包负责完整叙事。

## 3. 我们占的三个位置

1. **上下文治理组件（旗舰）**——当前无主的位置。预算分配、压缩、卸载、token 内省是确定性运行时工程（可测试、可复现），与记忆算法是两条赛道。所有主流框架都把它留给用户。
2. **契约中立层**——anyio/fsspec/slf4j 模式：不拥有实现，拥有"可互换性"本身。fsspec 没有把 S3 做得比 boto3 好，但它是文件系统的互换标准。`Memory` / `Sandbox` 端口冲这个位置。
3. **中立基准**——"我该用哪个 memory？"人人都在问、没有中立答案。随契约发布基准套件，让所有符合契约的实现可复现地比较。擂台不参赛，但比较都发生在擂台上。

## 4. 明确不打的三场仗

1. **不打记忆算法仗**：Mem0/Letta/Zep 在研究跑步机上（团队 + 数据飞轮），不追；
2. **不做全家桶 monolith**：抽象膨胀是 LangChain 被诟病最多的地方。发布即承诺——N 个精心维护的包好于 3N 个半维护的包；
3. **不做运行时插件容器**：理由见 [ADR-0001](decisions/0001-explicit-injection-over-service-locator.md)。

## 5. 增长模型

规模长在**组件数量**上，不长在内核复杂度上（cordis/Koishi 验证过的模型：内核几千行，生态几百个插件）。

- v1：core + context（旗舰）+ memory + sandbox + policy + providers + engine + 伞包；
- v2：orchestration（多 Agent 编排）、observe（trace/回放查看器）；
- v3：MCP、skills、评测 harness——每个都是新增一个 workspace 成员，不动内核、不动已有包；
- 生态轴：第三方组件**发布自己的顶层包**、只依赖 `tutelary-core`（先例：`langchain-openai` 之于 langchain）——`tutelary.*` 命名空间单方所有，不向第三方开放（`google.*` 同规）。

## 6. star 路径（诚实版）

star 与代码量不相关，与"承诺是否清晰 + demo 是否惊艳"强相关。执行顺序：

1. 先发旗舰单包 `tutelary-context` + 一篇 deep-dive + README 演示（token 瀑布图 /"这次运行为什么花了 80k"内省报告），攒第一批 star；
2. 跟进 memory、sandbox、policy，每包带 only-\* 示例与架构文档；
3. engine 与伞包最后上，作为"整船"叙事收口；
4. 契约基准 + 官方 Mem0 adapter 立住"中立"；
5. CI 的"每包隔离安装测试"写进 README 当卖点——对 à la carte 承诺的机器证明。

前几个月没有 star 是正常的：契约层是慢变量，deep-dive 文档与 demo 是前期增长引擎。

公开发布的时点排在开发计划 M5 之后，由项目所有者最终决定（M5 交付“发布就绪”）；本节顺序用于届时 M5 内部的发布排布。
