# 09 · 开发计划（M0–M4）

状态：活文档——每阶段收尾时更新 §5 勾选与本文修订，不追求预先精确。

**粒度契约**：本计划管到**阶段、顺序、验收与停损**，不管到文件与函数。文件级任务分解在各阶段开工时再展开（届时另立 `docs/plans/<日期>-m<N>-tasks.md`，本计划始终是它们的主控）。计划与实现冲突时：改计划，不硬扛。

## 1. 全局视图

一条关键路径，每阶段一句话使命：

```
M0 立规则 ──► M1 立旗舰 ──► M2 立广度 ──► M3 立整船（设计终审）──► M4 立中立 ──► M5 立对外
core+门禁      context+自用    memory/policy/sandbox   engine+伞包+双裁判    基准+Mem0    PyPI 全量首发
```

- 阶段间严格串行，关键路径只有一条（红线见 §3.1）；
- 两个设计检验点：**M0 末**——内核假设第一次被真实组件（context）消费；**M3 末**——双裁判，抽象的终审；
- 时间盒（含缓冲）：M0 1–2 周 / M1 2–3 周 / M2 3–4 周 / M3 3–4 周 / M4 2 周 / M5 1–2 周。超时不是失败：砍范围保验收（见 §4 末行）。

## 2. 阶段计划

### M0 · 内核与门禁（1–2 周）

- **使命**：把规则变成代码——core 四要素 + fakes + 架构门禁先于一切组件存在。
- **顺序**：types → events/Bus → ports → lifecycle/effect 栈 → assembler → fakes → 架构测试 6 条 → 契约插件骨架。理由：词先于法，法先于假实现——fakes 反过来检验 lifecycle 是否好用。
- **第 0 天 spike（发布形态验证）**：① uv workspace 可编辑安装后 `import tutelary.*` 正常；② 从构建好的 wheel 在全新 venv 单装 tutelary-core 后 import 正常。这是 PEP 420 命名空间的两个已知风险点（editable、单装），各验证一次；失败则降级为 langchain 式独立顶层包名（`tutelary_core` 等），只动 08 的命名规则，不动组件划分。
- **明确不做**：任何组件、engine、发布流水线（只搭 test.yml 骨架）；不公开发布。
- **验收**（07 M0 清单 + 一条自证）：core 零依赖证明绿；fail-fast 四种错误各有单测；装配中途失败回滚有单测；**用 fakes 拼一个"hello 装配"示例跑通**——内核自己的 only-\*。
- **停损**：assembler + bus 合计比任何一个未来组件还厚（语法比内容重）→ 回 [03](03-kernel.md) 砍机制。

### M1 · 旗舰与自用验证（2–3 周）⭐

- **使命**：context 做到真实可用——第一个被真实负载消费的组件，也是内核假设的第一次检验。
- **顺序**：预算模型 → **一个**压缩策略 → 卸载 → token 内省 → only-context → context 契约检查项。
- **关键纪律**：压缩策略必须压在**真实对话日志**上调参（自己的工作流即可，无需公开；对想象负载调参是本项目认定的最大学习陷阱）。
- **可判定判据（M1 开工时固化）**：开工（立 `docs/plans/<日期>-m1-tasks.md`）时建立小型固定评测集——3–5 段真实对话日志 × 若干预算档位，人工标注 must-survive 信息清单；此后“压缩质量”只认两条机器可判的硬指标：① 压缩后实测 token ≤ 预算声明；② must-survive 清单在压缩输出中全部保留。停损由硬指标触发，不走主观判断。
- **明确不做**：多种压缩策略、语义卸载高级玩法、向量记忆、**一切发布动作**。
- **验收**（07 M1 清单）：only-context（fake LLM）跑通；隔离安装绿；真实日志调参记录成底稿（为 M5 的 deep-dive 攒素材）。
- **停损**：评测集硬指标不达标 → 先补策略，同一评测集复测。无发布承诺，顺延零成本。

### M2 · 组件三连（3–4 周）

- **使命**：证明"组件可以一个接一个长出来"是流水而非巧合——顺序本身就是对内核的二次复检。
- **顺序**：memory（含 memory 契约检查项）→ policy → sandbox（平台依赖最重，放最后）。
- **每包固定节奏**：实现 → only-\* → 契约套件绿 → 隔离安装绿（发布统一在 M5）。
- **端口冒烟保险**：三包的端口签名在 M3 前没有真实循环消费者——memory 完成后写一次性 micro-loop（fake Provider + 真 memory/policy 喂一个傻循环）冒烟端口签名；一次性脚本，不作为交付物，只为压缩 M3 修订期的返工面。
- **超时砍序**：砍实现范围不砍验收；sandbox 预案为先延 DockerRuntime、保 SubprocessRuntime。
- **平台纪律**：开发机是 Windows、CI 以 Linux 为主——sandbox / policy 的平台差异（asyncio subprocess、路径、权限模型）在开工时显式决定测试的标注与跳过策略，不允许“本地全绿”实为单平台绿。
- **明确不做**：向量 provider（Markdown 先行——向量检索正是给第三方 Memory2 留的位置）、云沙箱后端。
- **验收**（07 M2 清单）：三包 only-\* 全绿；tutelary-memory 过自家契约套件。
- **停损**：任一包写不出 only-\* → 停下修边界，不硬写——裁判报警是流程在正常工作。

### M3 · 整船与终审（3–4 周）

- **使命**：engine 消费五端口，跑双裁判——抽象的验收，也是**预期内的端口修订期**。
- **顺序**：providers（两个协议即可：OpenAI 兼容 + Anthropic）→ engine（事件溯源循环 + Suspend 断点续跑）→ runtime 伞包门面 → full-agent 示例。
- **预期内变化**：engine 大概率逼端口增补（hooks、工具结果安检、子 Agent）——此时仍在 M5 首发前，按工作草案规则直接修订：实现改 → 文档同步 → 契约套件更新；M5 首发后才升级为 ADR + 版本语义。
- **明确不做**：多 Agent 编排（v2）、回放查看器 UI。
- **验收**（07 M3 双裁判）：full-agent 不改 core/组件一行跑通 + 全部 only-\* 跑通。两关都过抽象才算成立；跑不通 → 回炉，宁可延期。
- **停损**：端口修订超过两轮仍未收敛 → 内核词汇表有问题，回 03 重审，不继续缝。

### M4 · 立中立（2 周）

- **使命**：让"契约中立"从主张变成事实。
- **顺序**：基准 v0（memory workload，可复现）→ 官方 Mem0 adapter → 内置实现与 Mem0 同基准对比报告。
- **停损**：为适配 Mem0 需要扭曲端口 → 端口有偏向，ADR 修端口——这正是设 M4 的目的。

### M5 · 全量首发（1–2 周）

- **使命**：把做完并验收过的东西交给外部世界——发布是机械动作，排在一切验收之后。
- **发布决定权**：M5 的产出是“发布就绪”——全部验收绿、社区门面齐备、发布物料就位；真正的公开发布（PyPI 上架、打 tag、公告）由项目所有者在最后单独决定，不排期、不自动触发。
- **顺序**：占位清单执行 → 社区门面七件 → PyPI 逐包首发（core + context → memory / policy / sandbox → providers → engine + 伞包）→ README 演示、deep-dive 首篇、基准对比报告随发。
- **验收**：PyPI 全部可安装、隔离安装矩阵绿、demo 支撑"看懂并装上"。
- **停损**：发布准备中发现文档与实现冲突 → 修文档并顺延，不带病首发。

## 3. 贯穿全程的常量

1. **同时进行数 = 1**：任何时刻只有一个"进行中"组件。摊大饼（breadth before depth）是本计划认定的唯一死法；
2. **红线三条**（架构测试管，违反即爆红）：组件零横向依赖、只依赖 core、core 零外部依赖——不允许"先这样后面再改"；
3. **真实负载反馈**：M1 起每阶段必须有一个真实使用场景接住产出（自己的工作流 / 小工具均可），不许只对着自写测试跑；
4. **会话收尾纪律**：每次收尾全测试绿，不留红过夜；一个阶段可拆多个会话；
5. **文档义务**（阶段收尾动作清单）：勾 07 状态、更 09、写 CHANGELOG（若发布）、补 ADR（若决策变了）；
6. **扩展优先**：功能等价时永远选择给第三方留更大扩展空间的方案（[02 §4 原则 5](02-philosophy.md)）；各阶段验收（only-\*、契约套件、隔离安装）同时是可扩展性的机器证明。

## 4. 全局风险表（把控全局的核心）

| 风险 | 信号 | 对策 |
|---|---|---|
| 内核过度设计 | core 比组件厚、机制找不到消费者 | 回 03 砍机制——"语法不是管家" |
| 端口偏向内置实现 | 第三方 / Mem0 适配需要扭曲 | ADR 修端口；M4 是强制检查点 |
| 旗舰不惊艳 | 内省 demo 讲不出故事 | 推迟发布回真实负载——承诺未出，顺延零成本 |
| 摊大饼 | 想同时开两个组件 | 红线 1；冲动记入 backlog 不执行 |
| 文档腐烂 | 文档与实现冲突 | 阶段收尾文档义务 + 发布前"代码说了算" |
| 节奏衰减 | 连续两周无产出 | **砍范围不砍验收**：保 only-\* → 保发布 → 砍其余 |
